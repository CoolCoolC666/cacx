## 贯穿全部部分的三条设计约束

这三条不是风格问题，是被具体事故逼出来的，写报告时值得单独讲。

### ① 网页与 MCP 必须共用同一份实现

`cacx/web/app.py` 和 `cacx/mcp_server.py` 是两个入口，但**业务逻辑只写一遍**：
搜索、抽取、面板聚合都落在 `cacx/db.py` 与 `cacx/extract.py` 里，两个入口都调它。

代价是路由层必须抽 `_xxx_impl`。FastAPI 路由参数的默认值是 `Query(...)` **参数对象**而非数字，
走 HTTP 时框架会替换，走内部调用时不会——直接互相调用会 `TypeError` 炸掉。
所以凡是要被两处调用的逻辑，都抽成模块级 `_impl`，路由只做薄壳。

### ② 「屏幕 = 导出」是构造出来的，不是两处人工同步

面板快照导出（`/api/panel/snapshot`）与网页调的是**同一个函数、同一份参数**。
早先时间轴没做到这点：网页端自己在 JS 里算坐标画图，导出端另画一遍，
结果屏幕有、导出没有。改成服务端出图（`_timeline_impl` 把 SVG 塞进 payload）后，
两边逐字符相同，并且有测试钉住这条不变式。

### ③ 任何数字都要说清分母

界面上并列出现「发文量 4433 篇」和「有正文 4432 篇」不是凑数——
两者的分母真的不同（正文为空的列表页占位也算发文量），
不说清楚就会被质疑「为什么两个数不一样」。

关键词主题是**粗筛**口径，一篇可命中多类，各月相加会超过发文量；
AI 主题只统计**已被标注过**的文章，覆盖率 0/4432 时与发文量完全不可比。
这些限制都写在界面上，报告的「已知局限」一节也照抄。
