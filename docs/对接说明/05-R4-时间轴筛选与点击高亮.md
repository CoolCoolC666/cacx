> **结论：后端一行都不用改。** 只要前端把面板上的日期传过去。

### 2.2 要做的

在时间轴面板的工具条上（`index.html:602` 附近那一段，`主题口径` 那一行的下方）加两个日期控件 + 一个「按范围筛选 / 恢复全部」的按钮，然后在 `loadTimeline()` 里把 `date_from`/`date_to` 塞进 `q`。

### 2.3 必须遵守的约束（这几条都是踩过坑的）

1. **`months` 是「尾部 N 个月截断」，和日期范围是两件事，不要合并。**
   截断在**服务端**做（`months` 参数）。前端绝对不能自己 `slice()` 月份数组——一旦前端切一次、后端也切一次，网页和 CSV 导出口径就对不上。这是本项目「屏幕 = 导出」的老伤，`_timeline_impl` 的 docstring 里写着前车之鉴（曾经前端那份算错 `mx`，单根柱子高 2208px）。
   两个控件的语义建议写成：`日期范围 = 选哪一段时间`，`months = 这段范围里再看尾部几个月`。若用户觉得两个控件叠加太绕，可以只在日期范围生效时把 `months` 下拉置灰，但**不要偷偷改后端语义**。

2. **两张图共用同一个月份集合**（以发文量的区间为准）。发文量按「所有文章」数，主题按「有正文的文章」数，两个分母本来就不一样。别让它们各自按自己的区间出图，横轴长度不同并排看就像数据打架。

3. **末月通常不完整**（当月还没过完），最后一点天然偏低。界面上那句「末月未过完」必须继续显示，否则会被当成"发文量在跌"。加日期范围后，如果用户选的 `date_to` 就在当月，这句提示更重要。

4. **口径回显要跟着变**。`tl_note`（`index.html:3902` 附近）会打印 `d.scope.site` / `d.scope.range` / `d.scope.months` / 总篇数 / 有正文篇数。加了筛选后要确认这句回显反映的是**筛选后的**数字，否则用户会看到"我选了 2025 年，怎么还写着 4416 篇"。

5. **日期控件 id 不要叫 `date_from`/`date_to`**——那两个 id 已经被关系图谱页占了（`index.html:241-242`），同一个 HTML 文档里 id 重复会让 `$('date_from')` 取到错的那个。用 `tl_from` / `tl_to`。

6. `pn_site` / `pn_months` 变了要能触发重载（`loadPanel()` 已有 `onchange="loadTimeline()"` 的先例，照抄）。

### 2.4 验收标准

- 选 `2025-01-01 ～ 2025-12-31`，发文量图只剩 2025 的 12 个月，`tl_note` 里的合计篇数明显变小且与图上对得上。
- 日期范围留空 → 行为与改动前**完全一致**（默认走 `_PANEL_D0`/`_PANEL_D1`）。
- 选一个只有 1 篇文章的窄区间 → 图不炸，能画出一个点；不要出现除零 / 空数组异常。
- 点「⬇ 数据」导出的 CSV，行数 = 图上的点数（月份数），不含范围外的月份。
- 切到「AI 分类」口径后，以上都还成立。

## 3. 需求 2：图谱「高亮点击一下就可以」

### 3.1 现状

关系图谱页工具条上有「高亮」输入框（`index.html:365`，`id="gp_find"`，placeholder「找出并标黄」）+「清除高亮」按钮。用户必须**打字**才能高亮，想看的是键盘，`oninput` 去抖 320ms 后请求（`gpFindDebounce()`，`index.html:3860`）。

后端 `cacx/graph_analysis.py` 的 `to_pyvis_nodes_edges(..., find="")` 已经支持 `find`，返回 `find` / `find_hits` / `find_edge_hits`；节点命中条件是 `find in str(x["id"])`，颜色由 `_GRAPH_HIT_COLOR = "#ffd479"` 决定（`app.py`），前端对应 `GP_HIT_COLOR`（`index.html:1746`）。

### 3.2 ⚠ 先想清楚：点击高亮 ≠ 复用 find 语义

**这是本条需求最大的坑，不看这一段做出来的东西一定是错的。**

现有 `find` 的边命中规则是：**边命中的条件是两端都命中**（`e["from"] in hits and e["to"] in hits`）。当初这么定是因为搜「网信」这种词会命中几十个节点，如果只亮一端，几乎每条边都会亮，等于没筛。

但**点击一个节点**时，`find` 就是那个节点的名字 → 只会命中 **1 个节点**，而它的邻居都不叫这个名字 → **边命中数为 0** → 点完之后图上只有一个黄点，四周全暗。用户体验上等于什么都没发生。

所以点击高亮**不能直接把节点 id 塞进 `find`**，必须走另一条语义：

> **点击节点 → 高亮该节点 + 它的全部关联边（即它的邻居）**
> **点击边 → 高亮这条边的两个端点 + 该边**

这在交互语义上就是"聚焦"（现有 `focusNode()` 干了一半：它调 `selectNodes` + `focus` 把镜头拉过去，但**没有变色**，所以视觉上还是"哪儿都没变"）。

### 3.3 建议的实现方式（选一种，别两个都做）

**方案 A（推荐，改动最小、复用现成管道）**
在后端 `find` 之外增加一个 `focus` 参数（节点名或 `a→b`），语义为"聚焦"：
- `focus=<节点名>`：命中集合 = 该节点 + 所有与它有边的对端（**一跳邻居**，不包括二跳）
- `focus=<a>|<b>`：命中集合 = 恰好这 2 个节点 + 这 1 条边

前端只改渲染分支：`n.focus`/`e.focus` 命中时同样覆写 color + borderWidth，和现在 `n.hit` 的画法一致（`index.html:2132`）。

**方案 B（纯前端）**
不动后端，前端在 `GP_NET.on('click')`（`index.html:2171`）里维护一个 `GP_FOCUS` 集合，重绘时用 `GP_LEGEND_ON` 那套同款逻辑覆写颜色。好处是零后端改动，坏处是「屏幕 = 导出」这条不变量会破——导出件里就不带聚焦色了。

**倾向 A**，理由：导出 HTML 是演示的一部分，聚焦态导不出来会很奇怪。

### 3.4 点击行为怎么和现有交互共存

现在 `GP_NET.on('click')`（`index.html:2171`）已经接了：
- 点**边** → `showEdgeEvidence()` → 右侧列出原文证据句（老师要的核心交互，**绝对不能破坏**）
- 点**节点** → `focusNode()` → 选中 + 拉镜头 + 右侧显示 度/加权度/介数/PageRank/社区编号

新需求是把"点一下就高亮"接进来。推荐**在现有 click 里追加，不替换**：点节点时既拉镜头（保留）又设聚焦态（新增）；点边时既出原文证据（保留）又高亮这条边（新增）。再点同一个节点/同一条边 → 取消聚焦（toggle）。

同时保留原来的输入框，**不要删**——它搜的是"包含这个串的所有节点"，和点击的"精确这一个节点"是两种能力。

### 3.5 反馈必须明说

现有代码里已经踩过这个坑并留了警告（`index.html:2112`）：高亮结果**必须明说命中几个**，只靠变色不够——用户分不清是"确实没有"还是"高亮根本没生效"，而这两件事要做的动作完全相反。

点击聚焦也一样：点了之后要在计数区（`gp_cnt`）回一句 `◆ 聚焦「中央网信办」：1 个节点 / 243 条关系`。点击空白处 → 回 `点击节点或关系可聚焦；再次点击同一项取消`。

### 3.6 验收标准

- 点「中央网信办」节点 → 它和它的 243 条边一起变黄，其余变暗；右侧仍显示度/介数等详情；镜头拉过去。
- 再次点它 → 恢复原色。
- 点一条「中央网信办 → 工业和信息化部」的边 → 右侧仍列出原文证据句（回归重点），同时这两个节点 + 这条边变黄。
- 导出的 HTML 打开后能看到同样的聚焦态（方案 A）。
- 输入框功能完全不受影响，回归一遍。
- **规模不变**：不点任何东西时，仍是 300 节点 / 1410 边。高亮/聚焦只改颜色，**绝不裁图**。
