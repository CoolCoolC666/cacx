# 01 · 数据采集与双站接入

> 一句话：把「中央网信办」和「浙江网信网」两个站点的公开列表接口打通，
> 只读不登录，落到一个 SQLite 库里，后面的所有分析都从这里长出来。

## 1 这部分要解决的问题

任务要求「从 cac.gov.cn、zjwx.gov.cn 采集 2024 年以来数据」。两站的页面结构完全不同：

- **cac.gov.cn**（中央网信办）：列表分页参数在 URL 上，正文页有稳定的正文容器
- **zjwx.gov.cn**（浙江网信网）：栏目编码驱动的列表接口，正文页结构松散

如果为每个站写一套爬虫，后面加第三个站就要重写。所以拆成三层：
**通用采集器（`generic.py`）+ 站点配置（选择器写在配置里）+ 站点适配（`cac.py` / `zjwx.py`）**。
新站走配置，不写代码。

## 2 用户入口

| 入口 | 位置 |
|---|---|
| 网页 | 顶部「数据同步」页 → 开始同步 / 增量 / 查看同步记录 |
| 命令行 | `cacx sync --mode incremental`（`sync-latest.bat` 双击即跑） |
| MCP | `cacx_sync` 工具 |
| 加站点 | 网页「添加站点」表单，或 `cacx site add --id mysite --name "..." --url https://...` |
| 探测某页能否采 | 网页「站点探测」，或 `cacx site probe <URL>` |

## 3 与工具的接口面

### Web 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/sync` | 触发一次同步（参数含站点、模式、日期范围） |
| GET | `/api/sync/status` | 当前是否有任务在跑 |
| GET | `/api/sync/runs` | 历史同步记录 |
| GET | `/api/sites` | 已注册站点 |
| POST | `/api/sites` / `DELETE /api/sites/{code}` / `POST /api/sites/{code}/enabled` | 站点增删与启停 |
| POST | `/api/sites/probe` | 探测选择器（不落库） |
| POST | `/api/sites/probe-run` | 探测并**真抓一篇**，用于判断选择器是否真的能用 |

> ⚠ `probe` 与 `probe-run` 的区别是实测出来的：只跑 `probe` 看到「选择器命中 3 个」
> 并不代表正文页能抓——列表通了正文可能空。`probe-run` 会真打一次正文接口。
> 「实测不通」有两种可能：站点不通，或我这边不通。

### 核心模块

| 文件 | 职责 |
|---|---|
| `cacx/collector/base.py` | 采集器基类、失败分类枚举 |
| `cacx/collector/generic.py` | 通用采集器：按站点配置里的选择器抓列表 / 正文 |
| `cacx/collector/cac.py` | 中央网信办适配 |
| `cacx/collector/zjwx.py` | 浙江网信网适配 |
| `cacx/collector/rules.py` | 正则清洗规则（去导航、去站外链接、去版权尾） |
| `cacx/collector/classify.py` | 失败分类（导航页 / 站外跳转 / 脏数据 / 列表翻页失败…） |
| `cacx/collector/probe.py` | 站点探测：选择器能不能用 |
| `cacx/collector/runner.py` | 编排：列表 → 正文 → 入库 → 记录 |

### 数据表

| 表 | 当前行数 | 作用 |
|---|---|---|
| `articles` | 28 999 | 主表。一篇一行，含 `site` / `pub_day` / `url` / `content_text` / `content_empty` |
| `articles_fts` (+ `_data` / `_idx` / `_docsize` / `_config`) | 28 999 | SQLite FTS5 全文索引，中文用 `trigram` |
| `sync_runs` | 12 | 每次同步的起止、列出多少、新增多少、失败多少 |
| `external_links` | 132 | 站外链接及失败原因，供「链接抓取优化」用 |

`articles.content_empty` 是**占位标记**：列表页抓到了但正文没入库的条目。
它是「4 515 篇 vs 4 513 篇有正文」这两个数字差 2 的原因，
不是数据错误，但必须显式统计出来，否则会以为语料是完整的。

## 4 数据流

```
站点配置（config/sites.d/*.json 或 config/settings.json）
        │
        ▼
collector/runner.py 编排
        │
        ├─ 列表页/接口 ──► classify.py 失败分类 ──► 丢弃并记账
        │                          │
        │                          └─► sync_runs.failed
        ▼
  正文页（单篇、限速、可续跑）
        │
        ▼
  rules.py 清洗（去导航 / 去版权 / 去站外）
        │
        ▼
  db.upsert_article() ──► articles ──► db.rebuild_fts() ──► articles_fts
        │
        └─► external_links（站外链接单独记账）
```

## 5 口径与分母

- **入库条数 = 列出条数 − 失败条数 − 正文未抓到的条数**，三个数在 `sync_runs` 里都能查
- **2024 年以来有正文 = 4 513 篇**（cac 2 956 + zjwx 1 557），这是后面所有分析的分母
- **全库 28 999 篇**含 2024 年之前的数据，面板三张图都限定 `pub_day >= 2024-01-01`，
  就是为了对齐任务要求；不限定的话「按年分布」里会出现 2011、2013 这些早年尾巴
- 关键词类筛选里的「有正文」用 `content_empty = 0` 判定，不用 `chars > 0`——
  两者在历史数据上有过不一致

## 6 已知局限（写进报告）

1. **只读公开接口，不登录、不翻需要授权的页面**。因此语料是「公开发布的那部分」，
   不等于两站全部发文。报告里必须写明这是公开语料而非全量公文。
2. **列表翻页有上限**。两站的列表接口都只暴露有限页数，历史文章采不全；
   `sync_runs.listed` 与实际拿到多少条的差就是丢的部分。
3. **正文抓取失败会留占位**。有 69 条 `content_empty = 1`，
   它们计入发文量但不计入主题分析——所以两个分母必须分开报。
4. **清洗是规则式的**，不是模型判定。规则漏掉的噪声（页脚、版权声明、
   相关阅读列表）会残留在正文里，污染下游的关键词统计。
   这是「实体抽取出现碎片」的源头之一，见 [02](02-R1-实体与关系抽取.md)。
5. **没有定时自动同步**，目前靠手动点或跑 bat。增量同步本身是有的，
   但「每天自动跑一次」这层调度没做——写报告时不要写成「实时同步」。
