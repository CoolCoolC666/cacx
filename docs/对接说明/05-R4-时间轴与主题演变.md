# 05 · R4 时间轴与主题演变

> 一句话：老师要求的「时间轴」——发文量与主题随时间的变化。
> 两张图共用同一批月份，并且**图在服务端出**，网页与导出逐字符一致。

## 1 这部分要解决的问题

PPT 的第三项网站要求：「时间轴（发文量/主题随时间的变化）」。

看上去只是画两张折线，实际难点全在口径上：

- 发文量按「所有文章」数，主题按「有正文的文章」数，**两个分母本来就不一样**
- 末月通常还没过完，最后一点天然偏低，会被误读成「发文量在跌」
- 主题有两种口径（关键词粗筛 / AI 分类），必须能切换对比
- 屏幕看到的和导出的必须是同一张图

## 2 用户入口

「数据面板」页 → 往下滚 → **时间轴**区块。

区块上方一条控制带，与面板**共用**站点与月份筛选：

| 控件 | 作用 |
|---|---|
| 主题口径单选：关键词粗筛 / AI 分类 | 切换第二张图的口径 |
| 🤖 AI 标主题 | 对未标注文章跑 AI 打主题标签（先预览再真跑） |
| ⬇ 图 | 下载 PNG（2 倍分辨率，适合放进论文） |
| ⬇ 数据 | 下载 CSV |
| 口径回显行 | 常驻显示两站合计、日期范围、月份数、两个分母各是多少 |

## 3 与工具的接口面

### Web 接口

```
GET  /api/panel/timeline?site=&top=6&date_from=&date_to=&include_ai=true&months=36
POST /api/panel/ai-themes   {sites, limit, per_call, dry_run}
```

| 参数 | 说明 |
|---|---|
| `top` | 第二张图显示几类主题。**三处（网页 / CSV / 快照）统一取 `_TL_TOP = 6`** |
| `months` | 只截**尾部** N 个月，且**在服务端切** |
| `include_ai` | 是否计算 AI 口径 |
| `dry_run` | **默认 True**，只返回计划不调模型；真跑必须显式改 |

### 核心实现（都在 `cacx/web/app.py`）

| 名字 | 作用 |
|---|---|
| `_TL_TOP = 6` | 主题类数的**单一定义**。早先快照端用自己的 `limit` 当 top，网页出 6 类、导出出 10 类 |
| `_timeline_impl(site, top, date_from, date_to, include_ai, months_n)` | **唯一的实现**。网页路由与快照导出都调它 |
| `article_monthly_trend` | 按月发文量，**补零** |
| `problem_monthly` | 治理问题 × 月份（关键词粗筛），返回 `_kept` / `_dropped` |
| `ai_theme_monthly` | AI 标签 × 月份，可按传入月份对齐 |
| `theme_coverage` | AI 标注覆盖率 |
| `_svg_stack(...)` | **纯手绘 SVG 堆叠面积图**，零图表库 |
| `_tl_color(key)` | 按名字 crc32 取色（不用内置 hash——它按进程加盐，重启就变） |
| `_tick_idx(n, every)` | x 轴刻度下标，末尾太挤就让掉前一个 |

### AI 主题：`cacx/ai/tasks.py`

| 名字 | 作用 |
|---|---|
| `THEME_LABELS` | **受控词表 21 类**（含 `other` 兜底） |
| `theme_many(cfg, arts, dry_run, per_call=12)` | MiroFish 式批量 LLM 调用 |

**受控词表是硬要求**：模型自造的主题名（比如它自己编一个「网络新型犯罪」）
一律丢弃，并把丢弃计数显示出来。否则图例里会混进无法归类的碎片，
而且每次跑结果都不一样。

**批量调用**：多个请求打包成一次 API 调用，成本约降一半、速度升数倍。

## 4 数据流

```
 articles（pub_day ≥ 2024-01-01）
        │
        ├─► article_monthly_trend()  ──► months[]  {month, total, cac, zjwx}
        │       补零：中间没发文的月份补 0，不跳过
        │       截断上界：只有哨兵值（date_to ≥ 2099）才截到数据实际末月
        │
        ├─► problem_monthly(top=6) ──► trows[]   {month, total, problems{类:次数}}
        │       粗筛：关键词命中。一篇可命中多类
        │
        └─► ai_theme_monthly(months=同上) ──► airows[] {month, labeled, themes{类:次数}}
                只统计**已被标注过**的文章
        │
        ▼
  ⚠ 三者共用**同一批月份**（以发文量的区间为准）
        │
        ▼
  服务端出图 _svg_stack()
        ├─ charts.volume     发文量，按站点（cac / zjwx）堆叠
        ├─ charts.theme_kw   主题随时间（关键词粗筛）
        ├─ charts.theme_ai   主题随时间（AI 分类）
        └─ charts.* 附带图例（颜色按名字固定）
        │
        ├──► 网页：$('tl_vol').innerHTML = d.charts.volume
        └──► 快照导出：{tl["charts"]["volume"]}  ← 同一份 HTML
```

## 5 口径与分母

界面上常驻这行（P7 立下的规矩：任何数字型选择都要说清分母）：

> 口径：两站合计 · 2024-01-01 ~ 2099-12-31 · 34 个月 ·
> 发文量合计 **4 515 篇**，有正文 **4 513 篇**（两图分母不同）。
> 当前是 **关键词粗筛口径**：一篇可命中多类，各月相加会超过发文量。

切换到 AI 口径时这行会变成：

> 当前是 **AI 分类口径**：只统计已被 AI 标过主题的 **0** 篇，
> 没标过的不在这个分母里 —— 所以这里的量和发文量对不上是正常的。

### 三个必须写在界面上的限制

1. **两个分母不同**。发文量 4 515 / 有正文 4 513。差 2 条是正文为空的占位。
2. **末月未过完**。图上画一条虚线竖标 + 「末月未过完」文字。
   实测 2026-09 发文 194 篇（全期最高），2026-10 只有 8 篇——
   这个落差**不是发文量暴跌**，是当月没过完。不标出来必被误读。
3. **关键词粗筛可重复命中**。堆的是「命中次数」不是互斥分类，
   各月相加会超过该月发文量。

### AI 口径的现状

**尚未真跑模型**，`ai_annotations` 4 513 条全部是 `task='summarize'`，
`theme` 标注数为 **0**。所以现在切到 AI 口径显示的是空态提示。

⚠ 报告里**不要写成「我们用 AI 做了主题分类」**——那是没跑的。
可以写成「实现了受控词表约束的批量 AI 分类通道，因需消耗 API 配额、
本轮未启用，当前展示的是关键词粗筛口径」——这反而是加分项：
说明了为什么不用，也说明了怎么用。

### 踩过的坑（值得写进工程留痕）

1. **补零补出 912 个月**。`date_to` 默认 `2099-12-31`，
   补零一路补到 2099 年，其中 878 个月是空的，图右边拖一条八百个月的空白。
   修正：只有哨兵值才截断到数据实际覆盖到的末月。

2. **前端算 mx 算错，单根柱子 2208px**。容器只有 142px，整页被撑爆。
   根因是前端用类别名做 key 查找（`keyed.has(值)` 恒 false），累加恒为 0。
   改成服务端出图后，这类事故只剩一处可犯。

3. **钳制只做了一半**。堆叠图原来只钳「单层高度 ≤ plot_h」和「累计 base ≤ plot_h」，
   但两层各自顶满时「base + 本层」会跑到 `pad_t - plot_h` = **-192px**，已经在画布外。
   把 Y 轴上限函数打桩成返回 1（模拟「上限被低估」）当场顶出来这个洞。
   真正的兜底是坐标本身 `_clip` 到绘图区内。

4. **x 轴末尾标签叠字**。`i % every == 0 or i == n-1` 让最后两个标签
   相距不到半个字宽，糊成「2026056-10」。抽出 `_tick_idx()` 后消失。

## 6 已知局限（写进报告）

1. **关键词粗筛不等于人工标注**。一个议题可能同时命中两类
   （既是网络暴力又涉及未成年人），所以各行/各月相加会超过总数。
   这是粗筛的固有性质，只能靠标注说明来消解。

2. **AI 口径本轮未启用**，图上是空态。理由见上（配额 + 不可复现）。

3. **补零不等于「当月没发文」**。也可能是采集没抓到（翻页上限、失败分类）。
   补零是时间轴必需的（否则间距被压扁），但它掩盖了采集缺口——
   真要区分得看 `sync_runs`。

4. **末月永远是残缺的**。只要在当月看，末月就偏低。
   这是所有「按月统计」的固有问题，我们只做了标注，没做外推。

5. **主题类数固定 6**。超过 6 类的长尾被 `_dropped` 丢掉，
   但**丢掉的计数是可见的**——界面上会显示「另有 N 类未显示」，
   避免读者以为「就只有这 6 类问题」。
