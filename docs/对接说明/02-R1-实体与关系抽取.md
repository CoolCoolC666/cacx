# 02 · R1 实体与关系抽取

> 一句话：从正文里抽出「机构 / 政策 / 治理问题 / 措施」四类实体，
> 再抽出它们之间的关系，**每条关系都带原文句子**，这是后面能点回溯的前提。

## 1 这部分要解决的问题

老师的网站要求里有一条硬指标：**点每条边都能看到原文句子和来源链接**。
这意味着抽取阶段就必须把「证据」和「结论」一起存下来，
事后再去正文里搜是搜不出来的——同一句话可能多处出现，无法确定是哪一处。

所以 R1 的产物不是一张实体表，而是**实体 + 关系 + 证据三元组**。

## 3 与工具的接口面

### Web 接口

| 方法 | 路径 | 作用 |
|---|---|---|

### 核心模块 `cacx/extract.py`

纯规则，**不调用任何模型**。这是刻意的选择——报告里要写清楚理由。

| 函数 | 作用 |
|---|---|
| `split_sentences` / `sentence_at` | 中文断句，并保留**句子在原文中的字符偏移**（证据定位靠它） |
| `is_policy_name` | 政策名判定（「关于…的通知」「…的意见」「…方案」） |
| `find_measures` | 措施类实体（「组织开展」「加强…」「推进…」） |
| `_org_mentions` | 候选机构名扫描 |
| `_plausible_org` | 机构名合法性（长度、是否以「局/委/部/院/办/中心」等结尾、是否含标点） |
| `_drop_substring_orgs` | 去包含关系（「XX 网信办」与「网信办」只留更长且合法的那个） |
| `_problem_terms` | 治理问题关键词表 |
| `extract_article` | 单篇抽取，产出实体 + 关系 + 证据 |
| `_joint_pairs` | 同一句里出现的机构两两组合 → 联合发文候选 |
| `_tok_pos` | 分词定位（供政策名 / 措施抽取定位用） |
| `_build_relations` | 组装关系并挂上证据 |
| `extract_batch` | 批量 |
| `verify_evidence` | **自检**：证据句子是否真在原文里、偏移是否对得上 |

> `extractor` 全部是 `rule`——**没有一条来自模型**。这条数据本身就是报告的论点：
> 我们把 AI 放在旁路而不是主路上。

## 4 数据流

```
articles.content_text
        │
        ▼
  split_sentences()  ──► 句子列表 + 每句在原文的字符偏移
        │
        ├─► is_policy_name / _tok_pos   ──► policy
        ├─► find_measures                ──► measure
        ├─► _problem_terms（关键词粗筛）  ──► problem
        └─► _org_mentions → _plausible_org → _drop_substring_orgs ──► org
        │
        ▼
  _build_relations()
        ├─ 同句多机构 ──► _joint_pairs() ──► joint_issue（weight 累加）
        ├─ 政策/措施出现的问题 ──► target
        ├─ 机构 + 政策同句 ──► adopt
        └─ 机构 + 标题 ──► issue
        │
        ▼
  verify_evidence()  ← 证据必须能在原文里定位到，否则这条关系不写
        │
        ▼
  db.upsert_entities() / db.upsert_relations()
        （关系里冗余存一份 evidence 文本，即使 articles 被清也能回溯）
```

**为什么要 `verify_evidence` 这一步**：规则抽取一定会误判（见局限 1），
但只要证据句是真句，回溯时用户看到原文就能自己判断对不对——
**误判被降级成「需要人看一眼」，而不是「悄悄混进图里」**。
把精确率的问题交给证据透明度去兜。

## 5 口径与分母

- 关系数 8 801 是**全部**关系；图谱页默认画出来的是 1 633 节点 / 3 921 边，
  因为默认按关系类型与度数做了筛选。**两个数不是一回事，界面必须同时显示。**
- 按站点：cac 4 762 条、zjwx 4 039 条
- 按年：2024 = 2 448、2025 = 2 994、2026 = 3 359（2026 未过完）
- `weight` 是**该文章内**这条关系被规则命中的累计强度（每次命中 +2.0，
  标题含联合发布词或 `issue`/`target` 触发时 +3.0），**不是**置信概率，
  也**不是**「跨几篇文章共现」——同一篇里命中多次就会累加。详见 04 文档。

## 6 已知局限（写进报告，这一节建议原文引用）

1. **实体碎片污染——这是最诚实也最该写的一条。**
   实测 `org` 里混进了「大会主办」「结束二十国集团」这类**不是机构**的片段；
   `policy` 里混进了「我的祖国」（不是政策）和「年发展规划」（残缺）。
   成因是规则按句内位置与词性启发式切分，长定语会把动宾结构一起吃进来。

   已知清洗方向（可以写进「后续工作」）：
   - 提高 `_plausible_org` 的后缀白名单覆盖率，并要求机构名不跨标点
   - 对 `org` 做**别名归并**后再判合法性，减少同一机构被切成多段
   - `policy` 增加必须出现的结构词（关于/印发/的通知/的意见/的决定）
   - 引入词性标注或轻量模型做**二次确认**，但仍保留证据链

2. **关系类型靠共现，不是语义判断。**
   `joint_issue` 的含义是「同一句里一起出现」，两篇文章里两个机构各出现一次、
   但从不同句子，也能被判成联合发文——这是规则的代价。
   界面上已注明「按标题关键词粗筛，非精确统计；精确值以 R1 联合发文关系为准」。

3. **不做实体消歧**。同名机构（同名不同地）会被合并，
   所以 `top_orgs` 里带 `⚠` 标记的是机器归并**可能**误并的组，
   并附「机器挖掘的候选，非定论」的说明——这是**给复核用的标记，不是结论**。

4. **纯规则，天花板明确**。模型能做得更好，但我们刻意不用在主路上：
   模型不可复现、会烧配额、且一旦出错很难定位。
   AI 能力放在旁路（见 [07](07-AI能力与分词实验室.md)），要人工确认才入库。

5. **只抽了 4 类实体**。时间、地点、人物没抽，
   所以图谱里看不到「某次会议在哪开」这类时空维度。

6. **证据定位曾经系统性偏移（已修复，值得写进报告的过程）**。
   抽取时 `full = 标题 + "\n" + 正文`；而 `split_sentences` 返回的句子
   **含句尾分隔符**，所以标题行是 `'…意见》\n'`（长度 27），
   正文首句的起点也正好是 27。

   `sentence_at` 当时用闭区间 `start <= pos <= start + len(s)`：
   **pos=27 同时命中两句**，遍历先撞到标题就返回了 ——
   于是正文那句的关系全被挂上标题当证据。

   症状很好识别：**点边看证据，句子里的两个机构名都不出现**。
   修好之前那版库里，1311 条关系里有 **417 条如此（31.8%）**，
   而「标题 + 换行 + 正文」是公文最常见的结构，所以不是个例。

   修法：边界改**半开区间** `start <= pos < start + len(s)`，
   边界只归后一句；越界时返回空串而不是最后一句
   （返回「看起来像证据」的文本比返回空危险）。

   这条局限的价值在于：**它是靠「核对文档时顺手点了一条边」发现的，
   不是靠测试**。因为原来的测试只断言「证据句是原文的连续片段」，
   而标题本来就是原文片段——测试通过，功能却是错的。
   教训：**断言「产物合法」不等于断言「产物正确」**。
