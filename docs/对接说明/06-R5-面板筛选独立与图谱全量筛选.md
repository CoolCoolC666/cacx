## 3. 可行性结论

### 3.1 接口层：可行

`/api/graph/analysis` 实测（2026-10-15，`node_types` 全勾、`min_degree=2`）：

| 筛选 | 节点 / 边 | 画布 | 隐藏节点 | 建图耗时 |
|---|---|---|---|---|
| **不带日期（= 全库 2000-2026）** | **12162 / 29069** | 300 / 2995 | 11862 | 327.8s |
| 不带 site（网页日期框默认 2024-01） | 1761 / 4211 | 300 / 1482 | 1461 | 4.0s |
| `site=cac` + 2024-01 起 | 1201 / 3108 | 300 / 1367 | 901 | 2.5s |
| `site=zjwx` + 2024-01 起 | 1102 / 2431 | 300 / 1187 | 802 | 1.8s |
| 2024 全年 | 761 / 1575 | 300 / 1022 | 461 | 1.2s |
| 2026 全年 | 710 / 1547 | 300 / 1049 | 410 | 1.3s |
| `site=cac` + 2024 全年 | 506 / 1149 | 300 / 951 | 206 | 1.0s |

⚠ **两档口径**：第一行是**全库**口径（接口不传日期 = 全库，单次建图 237–385s，很慢；本表这一行 327.8s）；
第二行起是**分析窗**口径（网页日期框默认 `2024-01`），也就是屏幕上第一眼看到的数。
两档的节点 / 边 / 画布 / 隐藏节点**完全不同**，引用时必须标清是哪一档。

站点、日期、组合**全部生效**。要改的只有：app 三个 panel 路由透传 + `db.graph()` 加 JOIN。

### 3.2 数据层：可行但有边界

图谱筛的不是「文章全集」，而是「**已抽取关系的文章子集**」。
结果一定不大，**筛到没抽过的区间就是空的** —— 必须在界面上说明（见 T4）。

### 3.3 总结

| 问题 | 结论 |
|---|---|
| 图谱能吃站点/日期筛选吗 | **能**，analysis 已支持，边列表加 JOIN |
| 面板三张图能吃月份吗 | **能**，db 已有参数，只差路由 |
| 两边数字会相等吗 | **不会**：面板是文章口径（全库 28919 / 分析窗 4435），图谱是**已抽取关系**的子集（全库 6893 / 分析窗 1201）；同档比才成立（23.8% vs 27.1%），跨档比就是错的 |
| 筛出空图是坏了吗 | **不是**，是没抽过。界面必须说明 |

## 4. T1–T3：筛选贯通（最小改法）

### 4.1 T1 面板三张图接上日期筛选

**后端** `cacx/web/app.py`，三个路由各加两个参数并透传：

```python
@app.get("/api/panel/problems")
def api_panel_problems(site: str = "", date_from: str = "", date_to: str = ""):
    kw = {}
    if date_from: kw["date_from"] = date_from
    if date_to:   kw["date_to"] = date_to
    return {"items": _db().problem_distribution(site=site, **kw)}
```

`orgs`（注意保留 `limit`）与 `joint` 同理。

⚠ **空值语义要定死**：前端不传时后端收到 `""`，
**不要直接 `date_from=""` 透传** —— `a.pub_day >= ''` 在 SQLite 里恒真（碰巧对），
换 PostgreSQL 就错。一律用上面这种「空则不传、用 db 默认值」的写法。

**前端** `index.html:4277`，`s2` 换成带日期：

```js
const sq = new URLSearchParams();
if(site) sq.set('site', site);
if(df)   sq.set('date_from', df);
if(dt)   sq.set('date_to', dt);
const s2 = sq.toString() ? '?' + sq : '';
```

顶部加一对控件 `pn_from` / `pn_to`，与「近 N 个月」二选一：
**填了日期用日期，留空才用月份数** —— 这个优先级必须写进控件旁的说明文字。

### 4.2 T2 时间轴独立（方案 A）

改 `loadTimeline()`（`index.html:4159`）：

1. **删掉 `months` 的透传** —— 时间轴不再吃顶部「近 N 个月」。
2. 只传 `site` + `tl_from` + `tl_to`（R4 已有）。
3. 「恢复全部」清空 → 走服务端默认全区间。
4. 卡片标题旁写明：**「本图只受下方日期范围控制，不跟随面板顶部的月份数」**。

⚠ **别删服务端的 `months` 参数**（`_timeline_impl`）—— 导出还在用，
只是不再由顶部控件驱动。

### 4.3 T3 边列表接上筛选

**`cacx/db.py` · `graph()`** 两条 SQL 加 JOIN：

```sql
SELECT r.src_name, r.dst_name, r.rel_type, COUNT(*) n,
       GROUP_CONCAT(r.article_id) article_ids, SUM(r.weight) weight
FROM relations r JOIN articles a ON a.id = r.article_id
WHERE (? = '' OR a.site = ?) AND a.pub_day >= ? AND a.pub_day <= ?
GROUP BY r.src_name, r.dst_name, r.rel_type
ORDER BY n DESC LIMIT ?
```

节点那条同样 join（`entities r JOIN articles a`）。默认值对齐 analysis：`"" / "2024-01-01" / "2099-12-31"`。

**`index.html:2136`**：

```js
const g = await fetch('/api/graph?' + gpQuery()).then(x=>x.json());
```

即**复用 `gpQuery()`**，别再手拼一套 —— 两个参数集迟早会漂。

⚠ `limit` 上限 2000，而 `renderEdges()` 只渲染前 300 行，保持 300 一致即可。

## 5. T7：样本配置器 → 定制面板 + 标准

### 5.1 现状

`index.html:269` 的 `#v_sample` 是**抽样与抽取工具**（站点/栏目/起止/篇数上限/抽样策略），
**没有「面板」和「标准」的概念**。
另有一个 `dlSnapshot()`（`index.html:4064`）导出**整个面板**的 HTML —— 那是全量快照，
和「按配置生成定制面板」不是一回事，**别改错地方**。

### 5.2 (A) 面板配置 → 生成定制面板

| 配置 | 取值 | 作用 |
|---|---|---|
| 站点 / 栏目 / 日期范围 | 复用 `sp_*` 已有控件 | 口径 |
| 要包含哪几张图 | 多选 | 面板只画选中的 |
| 主题口径 | 关键词粗筛 / AI 分类（旁路） | 已有二选一 |

产出：只含勾选图的独立面板，顶部印出这组口径
（照 `drawBars` 里「口径：站点/年份范围」的做法）。

### 5.3 (B) 特定标准 → 达标判定

标准 = 阈值 + 判据 + 展示方式，三样都要有：

| 标准项 | 示例 | 实测现值 |
|---|---|---|
| 生成式 AI 占比阈值 | ≥ 10% 视为「已上升」 | 2024 4.5% / 2025 9.8% / 2026 14.5% |
| 月发文量阈值 | ≥ 150 篇视为「高峰月」 | 2024-09 180 / 2025-09 193 / 2026-09 191 |
| 关系覆盖率阈值 | ≥ 25% 视为「抽取正常」 | **27.1%**（2024+ 窗口 1201/4435；对 4433 篇有正文为 27.1%；全库 23.8%） |
| 证据可回溯率 | 必须 100% | 无证据关系 **0 条** |

**硬要求**：判定结果必须显示**判据原文**，不能只给「达标/不达标」。
否则老师问「凭什么达标」就答不上 —— 与项目既有原则一致（界面上每个数都要带口径）。

## 6. T5 / T6：数据补全（先词表，后 AI）

### 6.1 ⚠ 先读这条：AI 抽取的靶子只有 101 篇

2024+ 全部 4435 篇（其中 4433 篇有正文）的三分（**2026-10-15 补抽 19 篇后复测**）：

| 类别 | 篇数 | 占比 |
|---|---|---|
| ① 完全没抽过 | **606** | 13.7% |
| ② 抽过但 0 关系 | **2628** | 59.3% |
| ③ 已有关系 | 1201 | 27.1% |

**直觉上「3234 篇缺口」（① + ② = 606 + 2628）→「该上 AI 补」。实测后不是。**
（全库口径另有 2825 + 19201 = 22026 篇缺口。）

按「是否存在机构间协作信号」再切（强信号 = 联合印发/联合发布/联合公布/联合开展/会同/共同签署/共同发布；
弱信号 = 会见/贺电/致辞/出席。**2026-10-15 补抽 19 篇后复测**）：

| 类别 | 标题含强信号 | 正文开头 800 字含强信号 | 标题含**弱信号** |
|---|---|---|---|
| 缺口① 606 篇 | **1 篇（0.2%）** | **2 篇（0.3%）** | 193 篇（**31.8%**） |
| 缺口② 2628 篇 | 3 篇（0.1%） | 98 篇（3.7%） | 344 篇（13.1%） |

**结论**：
- 96.9% 的「缺口」文章**本来就没有机构间协作**（(3234 − 101) / 3234 = 96.9%），
  贺电、会见、纪念活动、名单公布、辟谣，AI 去抽也是空，**纯属浪费**。
- 缺口② 标题含联合类触发词的只有 **3 篇**，逐条看多数是「习近平同某国元首共同会见记者」——
  **这是领导人活动，不是机构间发文，抽了反而是噪声**。
- **AI 的真靶子上界 = 101 篇**（缺口两组里，标题或正文前 800 字命中强信号、去重后的篇数；
  缺口① 2 篇、缺口② 99 篇，均含标题与正文重叠去重）。

正文成本（缺口① 全跑也只有）：606 篇正文合计 21.0 万字符 ≈ **14.0 万 token**；
只跑 101 篇真靶子 ≈ **2–3 万 token**，几乎免费。

**但这条教训没贯彻到「会议/代表大会」上** —— 这是规则过宽造成的漏抽，不是数据问题。

**T5 做法**：
1. 逐个跑 `org_like()`，确认是被哪条规则否的（先写个 5 行脚本问，别猜）。
2. 精确修规则（如对「人民代表大会」「政治协商会议」这类**固定建制名**加白名单例外），
   **不要整类放开「会议/大会」** —— 那会把大量会议名放回图谱。
3. 改完重跑抽取，对比覆盖率变化，并把新数字同步到报告/README/演示脚本。

**这一项比 AI 抽取划算得多：没有 API 成本、没有噪声、没有不可复现性**
（AI 抽取违反项目「结果永远一致、可当场重跑」的原则，规则引擎不会）。

### 6.3 T6（最后做）：AI 抽取兜底

现有 AI 基建可复用（**都是现成的，别重写**）：

| 位置 | 能力 |
|---|---|
| `/api/ai/status` | AI 配置状态 |
| `/api/ai/failures`、`/api/ai/retry-failed` | 失败清单与重试 |
| `/api/ai/annotations/manual` | 人工标注 |
| `/api/panel/ai-themes` | **旁路预览，默认只预览不执行**（这个模式要沿用） |
| `/api/ai/summarize-batch` + `/{job_id}` | 批量任务 + 进度查询 |

配置已就绪：`provider=openai_compat`、`model=MiniMax-M3.1-Flash-Preview`，
**key 在 `config/settings.json`，绝不入库、绝不写进任何文档或日志**。

#### 6.3.1 定位（务必先写进代码注释）

AI 抽取是**兜底**，不是主力。理由见 §6.1：真靶子仅 101 篇，且其中相当部分
即便抽出来也只是「领导人会见」类噪声。

#### 6.3.2 输出必须与 rule 同构，且可区分

`entities` / `relations` 都有 `extractor` 字段，当前全是 `'rule'`。
AI 写的必须是 **`'ai:<model 名>'`**，例如 `ai:MiniMax-M3.1-Flash-Preview`。

⚠ **两种 extractor 混在一起不加区分，会让所有现有结论失效** ——
报告里「joint_issue 5425 条」（2024+ 窗口）这类数是纯 rule 口径。
所以图谱必须支持按 `extractor` 过滤，且**默认只显示 rule**。

#### 6.3.3 准入判据（硬性，否则污染图谱）

一条 AI 产出的关系要进 `relations`，必须**全部**满足：

1. `evidence` 是**原文的逐字子串**（入库前用 `in content_text` 校验，不通过就丢）。
2. **≥ 2 个机构主体**，且两端都能通过 `org_like()`。
3. 句子含**强协作动词**：联合印发 / 联合发布 / 联合公布 / 联合开展 / 联合部署 /
   共同发布 / 共同印发 / **共同签署** / 会同 / 联合签署。
4. **不含**领导人活动动词：会见 / 通话 / 贺电 / 贺信 / 致辞 / 出席 / 接待 / 慰问 / 唁电。
5. **不是国家元首间声明**（如「习近平同巴西总统卢拉共同签署联合声明」）——
   这类实测就在靶子里，但它不是机构间协作，抽进来会污染「网信办居中协调」的结论。

第 5 条尤其重要：§6.1 那 1 篇「标题含强信号」的缺口① 文章正是这种。

#### 6.3.4 落地形态

建议 **AI 结果先进候选表**（如 `relations_ai`），在界面上单独一页，
人工勾选后才并入 `relations`。理由与项目既有约定一致：
「AI 主题标注做成旁路，默认只预览不执行，没跑完之前不拿它的结果当结论」。

若时间不够，退而求其次：直接写 `relations` 但 `extractor='ai:…'`，
并保证图谱默认只画 rule —— 但**必须在界面上标出「本图含 AI 抽取结果」**。

#### 6.3.5 幂等与回滚

- 重跑不产生重复行（`extractor + article_id + src + dst + rel_type` 唯一）。
- 必须有一键回滚：删掉 `extractor LIKE 'ai:%'` 的行即可回到纯 rule 状态。

## 8. 项目铁律

1. 真值只有一个来源：**运行中的服务**。直连 db 算出来的数会和网页对不上。
2. 测试只读：**绝不写 `config/settings.json`、绝不写 `data/cacx.db`**；
   读真库用 `sqlite3.connect("file:data/cacx.db?mode=ro", uri=True)`。
3. 新增/改动测试必须**反向验证**：拆守卫确认会红，再 `shutil.copy2` 真还原 + sha256 校验。
4. 「屏幕 = 导出」：导出请求必须带**同一套**筛选参数。
5. 改后端接口先跑**可见浏览器验收**，不能只看 `--headless`。
6. 删文件走**系统回收站**，不用 `Remove-Item`。
7. 改 UTF-8 文件用编辑工具，**不要** `Get-Content | Set-Content`。
8. 报告/README/演示脚本里的数字与代码口径**必须同一套**，改一边就全改。
9. **API key 不入库、不进文档、不进日志。**

## 9. 不能碰的清单

- `cacx/extract.py` 的 `NEEDS_REVIEW_BELOW = 0.8` —— 门槛本身不动，只决定默认放不放行。
- `_blocked_for_graph()` 的**口径分离**（`blocked_all` 专供界面说明、`blocked` 供建图）——
  复用 `blocked_all` 当建图口径，会让「已放行 210 个措施」这句提示跟着消失。
- `gpQuery()` 里 `node_types` 的**两义性**：「全勾不传」会让措施类被当成「什么都没勾」→ 假开关。
- 时间轴 `_timeline_impl` 的 `months` **参数本身**（导出在用），只是不再由顶部控件驱动。
- `partial_last` / `last_month_partial` 的语义判定（末月 = 当前自然月才标未过完）。
- `_NOT_ORG_TAIL` / `_ORG_VERB` 的**整体框架** —— T5 只加精确例外，不整类放开
  「会议/大会」，那会把大量会议名放回图谱。
