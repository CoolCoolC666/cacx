# 04 · R3 机构合作网络与原文回溯

> 一句话：老师要求「点每条边能看到原文句子和来源链接」——
> 这一节讲的正是这条链路怎么打通的，以及现场演示时具体点哪两条。

## 1 这部分要解决的问题

前端的图只是壳，真正的要求在**证据**：
一条关系凭什么成立？它是从哪句话来的？那句话在原文哪个位置？原文链接是什么？

老师现场会点两条边看回溯，所以这条链路必须是**当场能演**的，
不能是「理论上能查」。

## 2 用户入口

「关系图谱」页 → **点击任意一条边** → 弹出证据面板。
面板里显示：关系类型、原文句子（高亮命中片段）、文章标题、发布日期、**原文链接**。

## 3 与工具的接口面

### 唯一的接口

```
GET /api/graph/evidence?src=<机构A>&dst=<机构B>&rel_type=<可选>&limit=50
```

签名：`api_graph_evidence(src: str, dst: str, rel_type: str = '', limit: int = Query(50, ge=1, le=200))`

返回结构（**以代码为准**，别照着想象写）：

```json
{ "items": [ { …relations 表的全部列…,
               "evidence":  "支撑这句的原文句子文本",
               "article_title": "文章标题",
               "pub_day":  "2024-03-15",
               "url":      "原文链接" } ] }
```

`items` 里的每一行是 **relations 的一行 JOIN articles**：
`src_name` / `dst_name` / `rel_type` / `article_id` / `evidence` / `weight` / `extractor`
再加上 `article_title` / `pub_day` / `url`。

两点容易写错、值得记住：

1. **正反向都查**。图是无向的（`build_graph` 建的是 `Graph`），
   存的却是 `src`/`dst` 有向，所以「A→B」和「B→A」可能是同一条关系。
   只按 `src = 参数` 查会**漏掉一半证据**。SQL 里写的是
   `(src=? AND dst=?) OR (src=? AND dst=?)`。
2. **排序是 `weight DESC, article_id`**，即**权重高的排前面**，
   不是按日期倒序。写文档时按「按发布日期倒序」讲是错的。

### 支撑的三处

| 位置 | 作用 |
|---|---|
| `extract.py: split_sentences` / `sentence_at` | 抽取时就把**句子在原文中的字符偏移**记下来 |
| `db.py: relation_evidence` | 按 (src, dst, rel_type) 取全部证据，**正反向都查** |
| `db.py: extract_sources` | 取**抽取引擎要用的原文清单**（id / title / url / content_text），不是导证据用的 |

`relations` 表里冗余存了一份 `evidence` 文本。
看似冗余（`articles.content_text` 里也有），但有两个实际好处：

1. **正文被清空或文章被 purge 后，关系仍在，证据仍可看**
2. 避免每次回溯都去扫 4 000 万字正文做偏移定位

## 4 数据流

```
 抽取阶段（一次性）
 ─────────────────────────────────────────────────────────
 content_text
   → split_sentences()  保留每句在原文的 [start, end) 偏移
   → 关系成立时，把该句的**文本**与**偏移**一并写入 relations.evidence
   → verify_evidence()  校验这句确实能在原文里按偏移取到

 回溯阶段（每次点击）
 ─────────────────────────────────────────────────────────
 用户点边 (A, B, co_issue)
   → GET /api/graph/evidence?src=A&dst=B
   → db.relation_evidence()
        SELECT r.*, a.title AS article_title, a.pub_day, a.url
        FROM relations r LEFT JOIN articles a ON a.id = r.article_id
        WHERE (r.src_name=A AND r.dst_name=B)
           OR (r.src_name=B AND r.dst_name=A)     ← 正反向都查
        ORDER BY r.weight DESC, r.article_id
        LIMIT ?
   → 句���直接来自 r.evidence 字段（抽取时就存好的，不是现场去正文里找的）
   → 前端展示 sentence + article_title + pub_day + url，
     并给「跳转原文」按钮
```

⚠ **没有「回原文按偏移再切一次」的兜底分支**——SQL 就是一次 JOIN。
所以「正文被清空后仍可看」这件事，靠的是 `relations.evidence` 里存了**句子文本**
（而不是只存偏移），不是靠运行时回查正文。

`verify_evidence` 是这条链路的**保险丝**：
抽取时如果证据句在原文里定位不到，这条关系**根本不会写进库**。
所以库里的每一条关系，回溯时必然拿得出句子——
不会出现「点开是空的」。

也正因为句子是**抽取时就存下来的文本**（不是偏移），
回溯是**纯读**操作：不碰 4 000 万字正文，不做切片，代价只有一次 JOIN。
演示时点边是**秒开**的，现场网络再差也不会卡。

## 5 口径与分母

- 一条边返回**多条**证据（`limit` 默认 50、上限 200）。一条 `co_issue` 边 `weight=17`，
  意味着 17 篇文章里这两个机构同句共现，界面上要显示「共现于 17 篇文章」。
- **排序按 `weight DESC`**：权重高的证据排前面（同一批里权重相同则按 article_id）。
  这不是随意的——共现次数多的关系更可能是真关系，演示时先点出它更有说服力。
- **`weight` 不是「共现篇数」，也不是置信度**。它是**该文章内**这条关系被规则
  命中的累计强度：每命中一次加 2.0（`co_issue` 标题含「联合印发/联合发布/会同」
  等触发词时加 3.0，`issue`/`target` 触发词命中也加 3.0），
  同一篇里命中多次就累加（写入时 `weight = relations.weight + excluded.weight`）。
  实测存在 `COUNT(DISTINCT article_id)=1` 而 `weight=50` 的边 —— 显然不是篇数。
  报告里不要写成「可信度 0.83」，也不要说成「跨 N 篇文章共现」；
  要讲强度就直接给数值并注明它是篇内命中强度。

### 演示用的两条备选关系

现场演示要求「点 2 条关系回溯原文」。下面两条是**用运行中的服务实测过的**，
不是凭印象写的 —— 实测口径：

| 检查项 | 判据 |
|---|---|
| 默认图上点得到 | 两个节点度都 ≥ 2，且默认筛选（`min_degree=2`）下这条边真的画出来了 |
| 证据句里有两端点 | 逐条查证据文本，两个机构名**都**出现在句子里 |
| 证据条数 | 现场网络差时不至于只点出一条 |

> ⚠ 演示前**仍然必须自己点一遍**。数据重抽一次这些数就会变，
> 而「库里查得到」**不等于**「页面上点得到」——
> 度数不够的节点、或被低置信规则踢掉的节点，根本不会画出来。

#### 备选 ① 中央网信办 ↔ 农业农村部（`co_issue`，24 条证据）

**原文句子**（50 字，逐字核对过；备选里两句里最短的）：

> 中央网信办、农业农村部、工业和信息化部联合印发《数字乡村高质量发展行动计划（2026—2030年）》

- **实测**：默认图上可点（度 243 / 34），24 条证据**全部**两端点名都在句里
- **额外优势**：这句话 cac.gov.cn 与 zjwx.gov.cn **两个站都转载了**，
  24 条里既有 2024 也有 2025、2026，日期筛选怎么调都点得到
- **为什么选它**：这条**真的是联合印发**，不只是共现。
  一句话里三个部委并列署名，能直接讲出「网信办的跨条线协调」，
  而且句子自带政策名，观众一看就懂
- **怎么讲**：「这条边不是我们连的，是原文里三个部委并列署名。
  您看，网信办在这儿是**牵头协调方**，具体落地在农业农村部。」
- **兜底**：同时连着「工业和信息化部」（实测 64 条证据，度 243 / 126），
  讲砸了可以顺手点另一条，证据更多、度数也更高更不容易点丢

#### 备选 ② 国家网信办 ↔ 网络数据安全风险评估办法（`issue`，3 条证据）

**原文句子**（67 字，逐字核对过，**中间那句「（以下简称《办法》）」不能省**）：

> 6月18日，国家网信办、工业和信息化部、公安部联合公布《网络数据安全风险评估办法》（以下简称《办法》），自2026年8月20日起施行。

- **实测**：默认图上可点（度 135 / 6），3 条证据全部两端点名都在句里
- **为什么选它**：它和备选 ① **是两种不同的关系类型** ——
  ① 是 `co_issue`（同一句里一起出现），② 是 `issue`（机构 → 发了这份文件）。
  连着点两条，正好把「图上不止一种线」讲清楚，而不是两次都在演示同一件事。
- **怎么讲**：「刚才那条是'谁和谁一起出现'，这条是'谁发的文'——
  线型不一样，含义也不一样。您看这句里还带了**施行日期**，
  这说明我们的关系能一路追到原文，时间线也对得上。」
- **兜底**：若被日期/站点筛掉了，切回备选 ①（日期范围很宽，2024–2026 都有）

**兜底话术**（老师追问时的准备）：

> 「`co_issue` 的口径是『同一句里一起出现』，**不必然等于联合发文**。
> 所以界面上把口径写在旁边，把每条边的原文摊开给您看——
> 这里有一条边，原文是『近日，中央网信办、国家发展改革委、
> 工业和信息化部、生态环境部、住房城乡建设部、农业农村部、商务部
> **七部门**联合印发《促进数字化绿色化协同转型发展实施方案
> （2026-2030年）』（以下简称《实施方案》），明确了"十五五"时期
> 推进数字化绿色化协同转型发展（以下简称双化协同）的思路目标、
> 重点任务和政策举措。』
>
> 那句长句子里确实同时点了七个部门，但我们把它记成 `co_issue`
> （同句共现），**没有**当成一条「七部门联合发文」写进报告。
> 换句话说：**我们宁可少认一条关系，也不把共现当成定论。**」

> ⚠ 这条长句**就在备选① 的 24 条证据列表里**（2026-09-04 那条，
> 权重 3.0，排在列表靠前），现场想指给对方看时直接往上翻就行。
> 实测：库里有 111 条关系共用这句七部门原文，涉及 12 个端点，
> 其中**没有一个是含连接词的碎片名** —— 低置信规则这一关是起作用的，
> 换句话说我们展示的这条长句本身也是「干净」的。

上面这段话术同时做到三件事：承认局限、展示证据、把判定权交还给观众。
比硬说「这就是联合发文」诚实，也比含糊说「可能是」有信息量。

## 6 已知局限（写进报告）

1. **「同句共现」不等于「联合发文」**。两篇文章里两个机构各出现一次、
   但在不同句子，也会被判成 `co_issue`。
   这是规则的固有代价，只能靠证据透明度缓解，不能靠口径声明消除。

2. **证据上限 50 条**。权重特别高的边可能截断，
   界面上要写明「共现于 N 篇，此处显示前 50 条」。

3. **原文链接依赖采集时的快照**。若原文后来被撤稿或改版，
   「跳转原文」可能打不开——正文库里有当时的快照，
   报告里可以提「已入库 4 513 篇正文，即使源站变动仍可查」。

4. **回溯只到句子，不到段落上下文**。
   句子脱离了前后文，偶尔会显得没头没尾——这是证据链的下一步待补项。

5. **`issue` 类关系（机构 → 发文）的依据是标题共现**，
   而标题是清洗过的，机构名写法在标题与正文中可能不一致，
   这类边的漏抽率高于 `co_issue`。
