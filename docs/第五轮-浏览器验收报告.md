## 与预期的偏差说明

1. **【提示 1】B6 增量 UI 文案的取法**：因「预览恒全量」，纯预览不会渲染「增量：…」行。为让该渲染分支跑到真数据，用 Playwright `route` 把预览请求体的 `mode` 改写为 `incremental`（`write` 仍为 `false`）回放，结果区出现「增量：新增处理 **81** 篇、跳过已有结果 **419** 篇。」。这是验证手法说明，**不是缺陷**；预览按钮恒全量的行为本身符合预期。
2. **【提示 2】D10 第一次只有 0.578s**：`limit=12` 且无日期限定的 orgs 本身并不慢，所以这一项证明的是「miss→put→hit 且响应逐字节一致」，真正证明「慢接口被缓存救回」的是 **D12（316.455s → 0.179s）**。
3. **【提示 3】** 见 D12 下方：11290/27309（无 `node_types`）与 12160/29049（四类全勾）是不同 key 口径，非矛盾。
4. **【提示 4】非本轮引入的既有显示瑕疵（不阻断）**：抽取结果卡片首行显示「实体 **0**： 机构 4029 …」「关系 **0**： 联合发文 877 …」——因为前端取 `r.entity_total||0`（`index.html:1835`/`1837`），而 `/api/extract/run` 的响应里没有这两个键（`extract_batch` 只回 `entities/relations/articles/skipped/skipped_reasons/low_confidence`）。已核对本轮前端提交 `8119039` 的 diff **未触碰该行**，属既有问题，建议下轮改为显示 `sum(types)` 或补后端字段。
