## 技术要求（重点，省掉你的踩坑时间）

### npm：随便用

技术方的**主工程允许用 React / Vue / Vite / npm**，
所以你写 React 组件、用 ECharts、跑 `npm run build` 都是合理的——
**代码质量与可维护性比什么都重要**，不要为了「双击能开」把代码写烂。

### 三种交付方式都可以，按你实际情况选

| 方式 | 交什么 | 适合 |
|---|---|---|
| **A. 单文件** | 一个自包含 HTML，库全部内联 | 想省事，或不熟构建工具 |
| **B. 工程 + 产物** | Vite/React 源码 + `build` 出来的自包含 HTML | 想把源码一起交（推荐） |
| **C. 纯源码** | 一个结构清晰的源码目录 + 一份 README 说明怎么跑起来 | 源码本身就是成果 |

**C 也是完全可以接受的**，理由很实在：

- 源码会被交给**其他智能体参考**，结构清晰比「能双击打开」更重要
- 一份干净的源码目录，比一个谁也改不动的压缩 HTML 有用得多
- 只要 README 里写清「装什么依赖、跑哪条命令、产物在哪」就算完整交付

### 无论选哪种，两条硬要求

1. **不要外链 CDN**：`<script src="https://cdn...">` 这种在没网的机器上
   只会得到一个空白页。库要么内联，要么走本地依赖。
   （选 B/C 时这由构建工具负责，你要确认 build 产物里确实没有外链）
2. **README 要能让人从零跑起来**：装什么、跑什么、产物在哪、出问题怎么办。

### 无论选哪种，都要交一张截图

**用浏览器打开最终产物并截图**。这张图要放进 PPT 和报告，
是别人不装环境也能看到成果的唯一途径。

### 图的交互细节（这些是加分项）

1. **节点按类型着色**：
   - 机构 = 蓝
   - 政策 = 紫
   - 治理问题 = 红
   - 措施 = 绿
   （自己定，但要**图上有图例**说明哪个颜色是什么）

2. **边的类型要能区分**：四种关系至少用不同线型或颜色。
   点击某类关系时，其他边变淡（聚焦），这样 200 条边的图才看得清。

3. **侧边栏内容**（点边后显示）：
   ```
   关系类型：针对
   中央网信办  →  网络谣言
   原文句子：「……（这里逐字显示 evidence_sentence）」
   来源文章：（标题，做成链接可点）
   [打开原文 ↗]
   ```

4. **规模控制**：如果关系超过 300 条，默认只画 **出现频次 Top 60** 的节点，
   其余折叠成「显示更多」。全画出来是没法看的。
